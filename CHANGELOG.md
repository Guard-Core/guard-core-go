-------------------

----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

guard-core-go v4.3.2 mirrors the guard-core 4.3.2 release: the reference's ReDoS static-safety chain ports verdict-exact onto the engine and takes over the pattern_safety corpus (the registry retires), the sus-patterns runtime registry lands with its telemetry and dynamic-rules application, engine-produced responses gain the custom_response_modifier pass, the websocket guard the adapters expose ports at the engine with suspicious counts shared with the HTTP pipeline, the remaining reference SecurityConfig surface arrives (fifteen knobs plus the performance-monitor wiring), and the lifecycle/state surface the Go adapters drive (manager exports, is_initialized, the cross-instance middleware state registry, MarkInitialized/AgentStats) closes the rows the fastapi-guard parity work left open. ### Added

- **The ReDoS static-safety trio, with the pattern_safety corpus going registry-free** (#58): a Python-re-compatible pattern parser (`guardcore/redos_parser.go` + `redos_escape.go`, sre_parse's group numbering and octal-vs-group-reference disambiguation mirrored) feeding the ordered structural prefilters (`redos_structure.go`, `redos_terminator.go`, `redos_ambiguous.go`), the dangerous-construct gate with the reference's three regexes verbatim (`redos_prefilters.go`), the reach-probe cost machinery (probe synthesis, interval algebra, class-intersection units, adversarial literal runs, `redos_reach_probe.go` and friends), stray verification against the compiled engine under a MatchTimeout and the cost arbiter (size ladders, growth-ratio extrapolation to the content cap, load-factor normalization, the measured-override branch) with the fail-closed equivalent of the reference's killable subprocess, and `ValidatePatternSafety` (`redos_compiler.go`) reproducing `validate_pattern_safety`'s chain order. `go_safety_xfail.json` is deleted and its 54 cases come off the registry with matching verdicts and reason classes (94/94 pass, 0 divergences, and the runner fails on a re-added baseline file); a CodeQL-flagged uint32-to-rune narrowing in `parseHexEscape` is bound-checked before conversion.
- **The sus-patterns runtime registry, pattern events and dynamic-rules application** (#59): the `SusPatternsManager` runtime registry (the reference module singleton as the package default) with safety-validated `AddPattern`/`RemovePattern` (custom entries dedupe and persist through the `patterns/custom` Redis key), the Redis-persisted custom restore on `InitializeRedis`, `DetectPatternMatch` (redacted regex identity, the `semantic:` prefix, the unknown fallback), and the manager's `Detect` running the shipped corpus scan plus the runtime registry with the reference `pattern_detected` envelope; `SecurityEvent` gains the `pattern_matched` column, the pipeline's penetration detection rides the manager so runtime patterns participate, and the dynamic-rules `suspicious_patterns` application is real (every pattern runs the registry's safety-validated add, rejections log with the reference honesty). The three sus-patterns event xfails leave the registry (6 to 3, the rest being host error-text renderings).

v4.3.1 (2026-10-07)
-------------------

The family-parity release: route-id ownership with per-route behavioral counters, the trusted-proxy XFF chain walk, agent event enrichment, the composite/OTel/Logfire agent handlers, structured JSON logging and the cost-parity detection loop
----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

guard-core-go v4.3.1 tracks the guard-core 4.3.1 engine release from the consumer side: the route-id ownership contract from @HardMax71's report lands (every decorated endpoint owns its route id, and behavioral counters key on it), the trusted-proxy identity resolution walks the X-Forwarded-For chain exactly like the reference instead of keying every verdict on the proxy IP, the agent stream gains the reference enrichment tier and the pluggable composite/OTel/Logfire handlers with structured JSON logging, and the detection loop carries the cross-engine cost-parity program (literal prefilter, rune-API scan migration, fail-closed cost ceilings) with verdicts pinned unchanged.

### Added

- **Agent event enrichment: the reference enrichment tier** (`guardcore/enricher.go`, #56): the eight `guard.*` wire keys (project id, service name, deployment environment, threat score, rule id/version, behavior correlation key plus the recent event count), `ThreatScoreFor`'s deterministic per-type map (default 20), the 300s behavior-correlation window and the `sha256(ip|service|bucket)[:16]` correlation key, with the enrichment order mirroring the reference strategy chain (identity, threat score, rule correlation, behavior correlation) and events without a metadata map shipping unenriched like `enrich_event`'s early return; `CompositeAgentHandler` gains the reference's enricher parameter (filter, enrich, then fan out), `SecurityConfig` the `EnableEnrichment`/`AgentProjectID`/`OtelServiceName`/`OtelResourceAttributes` block with the reference validation, the installed engine stream wraps the raw handler in the enriching composite with the live `DynamicRuleManager` as the rule-correlation matcher, and redaction is untouched (the bus still redacts at event build; enrichment only adds derived non-sensitive `guard.*` keys) (#56).
- **The composite, OTel and Logfire agent handlers plus the adaptation seam** (#55): `CompositeAgentHandler` fans out to N sinks behind the `EventFilter` mute lists with per-child failure isolation (a failing sink is logged, never propagated), start-degradation tracking (`Started`/`Degraded`/`FailedHandlers`), `Stop`/`Flush` fan-out, dynamic rules resolved from the first child that provides them and all-children health; `OtelHandler` renders security events as `guard.event.<type>` spans with the `guard.*` attribute set and W3C traceparent linkage and maps metrics onto the `guard.request.duration` histogram and the `guard.request.count`/`guard.error.count` counters, speaking OTLP/HTTP JSON directly (guardcore keeps its three-direct-dependency rule and owns no global provider state); `LogfireHandler` emits events as spans and metrics as `guard.metric.<type>` structured log records over OTLP toward the Logfire API with the reference's already-configured guard reproduced as a per-process claim; and `AgentHandlerFunc` is the interface-mismatch alignment (guard-agent-go's context-carrying `SendEvent` and its own SecurityEvent wire type wrap through the seam onto the engine stream unchanged) (#55).
- **Structured JSON logging with the `setup_custom_logging` parity surface** (`guardcore/logging_json.go`, #55): `JsonFormatter` renders the reference record shape one JSON object per line (timestamp in the Python asctime format, level, logger, message) while the reference text line stays the default, and `SetupCustomLogging(logFile, logFormat)` (re)installs the guardcore stream with own-handler replacement semantics, console+file fan-out, the unwritable-path fallback and the `restoreStandardLogging` escape hatch; `SecurityConfig.LogFormat` (text|json, validated) and `LogFile` wire through `NewEngine` before any manager is built, mirroring the reference middleware's construction-time `setup_custom_logging` call (#55).
- **The cost-parity detection program** (`guardcore/literal_prefilter.go`, `cost_budget_test.go` + the 9-case `cost_bodies` corpus suite, #54): the tempered-loop anchored recon families skip when none of their alternation literals occur in the text (a match-impossible condition, so verdicts cannot change; the extractor is unit-tested against the full pattern table to fire only on the intended shapes), the base64 scan loops migrate to the rune API (convert once, scan runes; the string API re-converted the remaining suffix to runes on every match attempt, quadratic across a scan), and the corpus's self-relative scan-cost ceilings are enforced fail-closed (K=5 x the 8 KiB anchor's linear projection + 250 ms floor; a workload over ceiling fails and an entry listed as over ceiling that returns under it fails too). Measured: 8 KiB 54.1 -> 20.0 ms, 64 KiB 1100 -> 142 ms, 256 KiB 12253 -> 710 ms, 1 MiB 138586 -> 4626 ms; verdicts 193/193 unchanged; the full conformance+cost run drops from 635 s to 25.8 s (#54).

### Fixed

- **Route-id ownership and per-route behavioral counters** (reported by @HardMax71 in guard-core #140; the reference fix shipped in guard-core #141/#142 and 4.3.1): endpoints built by one decorator factory (or one handler-wrapper table) share one `RouteConfig` only when they share a route id - the Go registry grants every `Routes.Register(routeID, ...)` call its own `RouteConfig` instance, so there is no shared-config last-wins overwrite to fix on this side, and the adapter contract (`RequestState.GuardRouteID`, the adapters' `WithRouteID` helpers) pins one id per decorated endpoint. `GetEndpointID` now resolves exactly like the reference `get_endpoint_id`: the request's route id wins, then the runtime-provided `guard_endpoint_id` extra, else `METHOD:redacted-path` - previously the route id was never read, so behavioral usage/return counters keyed on `METHOD:path` and collapsed across routes sharing a path shape (#141, #142).
- **The trusted-proxy XFF chain walk** (`guardcore/ipextraction.go`, the `ip_extraction.py` parity, #55): the reference resolves the client identity through `X-Forwarded-For` when the direct peer is a configured trusted proxy; this port shipped peer-address-only resolution, so behind a load balancer bans, rate limits, geo rules and behavioral keys all keyed on the proxy IP, and `TrustedProxyDepth` was validated but never read. Faithful port: CIDR-aware trusted-peer matching (mapped forms resolve through the prefix, bare entries match textually like the reference), the depth-selected entry counting from the right with the right-to-left walk taking over when the depth over-counts hops, chain-shorter-than-depth/malformed/all-trusted chains keeping the peer, the untrusted-peer spoof arm (handler-direct `suspicious_request`, handler `ip_extraction`, action `spoofing_detected`, the redacted display chain at debug level for private/loopback peers), the four once-per-process drift warnings carrying the reference texts, and `Engine.Check` resolving and caching the identity into `RequestState.ClientIP` before the pipeline so every consumer (rate limits, bans, geo, behavioral keys, events, block hooks) keys on the resolved client (#55).

-------------------

### Added

- **Geo country blocking: `WhitelistCountries`/`BlockedCountries` and the route-level country rules are now enforced by the `ip_security` check.** Both fields were declared on the config but fail-closed rejected (`UnsupportedFeatureError`), so no geo verdict could ever run. Ported from the reference country surface (`_utils/access_control.py` `_resolve_country_verdict`/`check_ip_access`/`_check_blocked_countries_detail`, `core/checks/helpers.py` `check_country_access`/`check_route_ip_access`/`_route_country_whitelist_matched`, plus `ip_security.py`): the global stage runs after the global IP lists and before the cloud-provider verdict, a global `Whitelist` match or a route `WhitelistCountries` match skips the country stage entirely, loopback IPs are exempt from the global stage only (the route stage denies unresolved loopback under an allowlist, like the reference), and an unresolved country fails closed in allowlist mode (generic `IP <ip> not in global allowlist/blocklist` stash) and open in blocklist mode. A resolved verdict denies with the reference reason (`IP from blocked country: <cc>`, `country_restriction` trigger stash, 403 `Forbidden`); the route stage combines the country verdict with the route IP verdicts (any deny denies) while keeping the `IP not allowed by route config` route shape. `ExemptIPs` never opens the country gate: the exempt flag still only sets once every deny check passed, so an exempt IP from a blocked country stays blocked. Config surface: country entries are uppercased and deduplicated like the reference `coerce_country_set` (ISO codes are not format-validated, matching the reference), both lists set is valid but logs the reference allowlist-shadows-blocklist warning, and country rules with no resolver fail config construction mirroring the reference `geo_ip_handler is required` error. Resolution ships the `CountryResolver` seam (`GetCountry(ip) (string, bool)`, the reference `GeoIPHandler` lookup half) with a built-in `GeoIPManager` reading a locally provisioned MMDB file via `GeoIPDBPath` (new `maxminddb-golang` dependency, the reference's `maxminddb` extra); the IPInfo token download/refresh lifecycle, the Redis-cached database copy, and `country_blocked`/`decorator_violation` events stay deferred (see KNOWN_GAPS "Geo country rules").
- **CORS support: the engine now runs the reference `CorsHandler` and its preflight short-circuit instead of fail-closed rejecting `EnableCORS`.** Ported from guard_core `handlers/cors_handler.py` with the field defaults of the `cors_*` SecurityConfig fields (`_security_config_fields.py`): `EnableCORS` plus `CORSAllowOrigins` (default `["*"]`), `CORSAllowMethods` (default `GET, POST, PUT, PATCH, DELETE, OPTIONS`, uppercased at validation, an empty list falling back to `["GET"]` like the reference `or` default), `CORSAllowHeaders` (default `["*"]`, lowercased), `CORSAllowCredentials`, `CORSExposeHeaders`, and `CORSMaxAge` (default `600`, a configured `0` falling back like `config.cors_max_age or 600`). The wildcard-origin plus credentials misconfiguration fails config construction with the reference message. Dispatch mirrors the adapter contract (fastapi-guard `guard/middleware.py` `_handle_preflight` / `_inject_cors_headers`): a preflight (OPTIONS carrying `Access-Control-Request-Method`) executes the security pipeline first and is then short-circuited with `200 OK` or `400 Disallowed CORS: origin, method, headers` (the verdict headers are attached before the failure decision, so the 400 still carries allow-methods/max-age/credentials), and every blocked response the engine returns composes the CORS verdict headers on top of the #22 security-header set exactly like the reference blocked path. A disallowed origin on a normal request simply gets no CORS headers (the browser enforces), and no-origin requests are untouched. For pass-through responses the new `Engine.CORSResponseHeaders(req)` hands adapters the per-request CORS map (Vary, Allow-Origin echoing the request origin or `*`, Allow-Credentials, Expose-Headers) to merge with `Engine.ResponseHeaders()`, mirroring `_inject_cors_headers`.
- **Per-route `RouteConfig.IPWhitelist`/`IPBlacklist` are now enforced by the `ip_security` check.** Both fields were declared on the route config but had zero consumers, so a route decorator's `require_ip`/`block_ip` rules were silently inert. The check now runs the route stage ahead of the global stage, mirroring the reference `check_route_ip_access` (guard_core `core/checks/helpers.py`) and its TypeScript port `checkRouteIpAccess`: the route blacklist denies its matches first (before any whitelist verdict or identity flag can clear them), a configured route whitelist takes over the route verdict (a match passes the route, a miss denies with 403 `Forbidden` and the `IP not allowed by route config: <ip>` block stash), and a route `IPWhitelist` clears the `IsWhitelisted`/`IsExempt` identity flags for the request exactly like the reference `skip_ip_lists` gate (`_resolve_is_whitelisted`/`_resolve_is_exempt`), so the exemption no longer skips rate limiting on that route. The global lists keep the final say: a route whitelist match does not relax the global blacklist or the global whitelist gate. Route lists match with the exact/CIDR semantics of `ipMatchesList`; the exclusion-scoped path ignores route rules (the reference passes `route_config=None` there), and the `ip` bypass skips the whole stage. Previously-routed requests without IP lists are untouched.
- **Security headers management: the engine now computes the reference's default security header set and adapters apply it to every response.** Ported from guard_core `handlers/security_headers_handler.py` with the field defaults of `SecurityConfig.security_headers` (`_security_config_fields.py`): the new `SecurityConfig.SecurityHeaders` block defaults to enabled with the ten class-default headers (`X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `X-XSS-Protection: 1; mode=block`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: geolocation=(), microphone=(), camera=()`, `X-Permitted-Cross-Domain-Policies: none`, `X-Download-Options: noopen`, COEP/COOP/CORP `require-corp`/`same-origin`/`same-origin`) plus `Strict-Transport-Security: max-age=31536000; includeSubDomains`. The `hsts` block builds `max-age`/`includeSubDomains`/`preload` with the reference preload corrections (preload requires at least one year and subdomains), an ordered `csp` block joins directives into `Content-Security-Policy`, the five override keys replace their headers (an empty override keeps the class default; the three-way `PermissionsPolicy` keeps, removes or overrides like the reference's falsy check), and `custom` headers land last and may override anything. Blocked responses carry the headers engine-side (every pipeline error response, including the fail-secure 500s, mirroring the reference error factory's `apply_security_headers`), and the new `Engine.ResponseHeaders()` API hands adapters the pass-through set to apply on the way out, mirroring `process_response`. Validation is fail-closed at config construction like the reference `configure()` raising: RFC 7230 token names for custom headers, CRLF rejected, values capped at 8192 bytes, control characters sanitized away. Disabling the block (or setting it to nil) removes every security header, matching `security_headers` falsy or `enabled: false` in the reference.
- **`SecurityConfig.ExemptIPs`: a skip-list that lets known-friendly automation bypass throttling without closing the door on everyone else.** A non-empty `Whitelist` is also an allowlist (every unlisted IP is denied by the IP check), so a public API previously had no way to exempt a monitoring probe, a VPN egress, or a partner's server from rate limiting. The new field accepts IPs and CIDRs with exactly the whitelist's validation (`validateIPList`, invalid entries fail config construction) and matching (`ipMatchesList`: exact, CIDR, IPv4-mapped) semantics. An exempt match sets `RequestState.IsExempt` after every deny check passed (it never opens the whitelist gate or adds a deny path), and exactly three skip points honor it: rate limiting, the user-agent check, and per-route cloud-provider blocks (the global `BlockCloudProviders` list still applies, mirroring the reference where the global list is enforced before the exempt flag can matter). Deliberately still applied to exempt IPs: the blacklist, dynamic bans, penetration detection and its violation counting/auto-ban escalation, and everything else. Parity with upstream guard-core `exempt_ips` (PR #118); the per-route `block_ip`/`require_ip` interplay is enforced by the `ip_security` check (see the route IP list entry above).
- **`SecurityConfig.ExcludedDetectionHeaders` now carries the reference's excluded-header semantics instead of a blind skip.** The field existed since the v1 config subset, but the header loop dropped an excluded header from the detection scan outright, so a SQLi or XSS payload smuggled through `X-Forwarded-For` or any configured exclusion went unseen, and the scan had no hardcoded proxy identity set at all, so a bare `x-forwarded-for: 192.168.65.1` false-positived the ssrf category. The header loop now routes through the reference's exclusion shape (`guard_core/_utils/detection_config.py`): the new `DefaultExcludedHeaders` set (24 proxy identity, forwarding and browser-fingerprint headers) merges with the configured map (entries lowercased), and an excluded header scans with every enabled category except the ones its value is known to false-positive. The skip is `ssrf` only, and only when the header is address-carrying (`_HEADER_CATEGORY_EXCLUSIONS`: host, origin, the forwarding family, the client-ip family, via) or its whole value parses as an address chain (`_strip_forwarded_entry_port` + comma-token IP parsing, so `10.0.0.5, 172.16.0.1` reads as a proxy chain while `203.0.113.10' OR '1'='1` still detects as sqli). Empty config on an ordinary header keeps the previous full-category behavior. Parity with upstream guard-core `excluded_detection_headers`.

### Fixed

- **Embedded JSON inside form and multipart field values now also scans the raw value after a clean walk.** The embedded-JSON walk replaced the raw value scan whenever the field value parsed as a JSON object or array, so a payload confined to the raw text (a duplicate-key remnant the walk drops, or text living in the JSON structure itself) was invisible whenever every walked leaf looked innocent. The extraction now emits the walk leaves first and the raw value afterwards with the field context (and the raw leaf string after a nested re-parse walk, with the walk context), mirroring the reference's `_check_value_enhanced` order: the embedded-JSON walk short-circuits the raw scan only when a leaf hits, and a clean walk that reports nothing falls through to the raw-value detect. The top-level JSON body walk and the parse-failure blob fallback are unchanged. Parity with upstream guard-core `_utils/embedded_json_scan.py` / `_check_value_enhanced` (the same fall-through the merged PHP port guard-core-php #18 kept).
- **Backslash-prefixed recon probes such as `\default` detect again.** The preprocessing pipeline's LDAP hex escape decoder folds `\de` sequences into single characters before the pattern tables run, so a query or body value like `\default` arrived at the recon rows as `Þfault` and matched nothing. The recon-category rows are now also scanned against the signal-preserving raw view (unicode normalization only, backslashes intact) via a new `reconRawViewPatternSources` set derived from the pattern table; the leading-separator gate applies to raw-view matches exactly as everywhere else, so bare words (`default`, `SAP`, `README.md`) stay innocent in query and body contexts, separator-prefixed probes (`\default`, `\README.md`, `\report.asp`) detect again, url_path and unknown contexts are unchanged, and a row matching both the processed and the raw view on the same text is counted once instead of doubling the threat score (raw-pass threats are deduplicated against the processed-view threats keyed on pattern and match text, merged processed-then-raw). Parity with upstream guard-core `fix/raw-view-recon-scan` (the reference fix for the cross-engine divergence documented in the 2026-09-25 detection audit; the Rust port, guard-core-rs #21, copies the same view-membership change).
- **The request body is now scanned: urlencoded forms, multipart parts with binary islands, and JSON walks.** `detectThreat` previously only scanned the URL path, query parameters, and headers, so every attack that arrived inside a request body was invisible; the pipeline now reads the buffered request body (capped at `Detection.MaxBodyInspectBytes`), routes it by content type, and scans every extracted value with the Python engine's context labels: urlencoded field names and values (`request_body`, `request_body:form_field`), multipart labels and entries (`request_body:multipart_field`, with RFC 7578 filename detection, part headers, and the `filename="..."` entry the file-upload rows match on), JSON bodies walked depth-first in insertion order (keys checked against `excluded_detection_body_fields` and the mongo-operator registry, leaves scanned like the reference), and plain or unknown bodies as one whole `request_body` value. Embedded JSON inside form or multipart field values walks first with the `:embedded_json` leaf suffix, exactly like the reference's embedded-JSON-first order. File-part payloads that are binary-like (artifact characters fill at least a fifth of the part) are reduced to printable runs of at least the new `DetectionBinaryMinRunLength` field (default 16, validated to `[4, 1024]` like the Python pydantic constraint) and each island is scanned on its own, so compressed uploads stop producing attack-shaped noise while text embedded in uploads still detects; whole-body fallback scans are never island-reduced. The multipart scanner is a line-based port of the Python email feedparser tolerances (raw header names and case, folded header values, colonless lines joining the payload, preamble/epilogue, nested `multipart/*` containers walked in place, missing final boundary tolerated, zero leaf parts falling back to the whole-body blob scan). Parity with upstream guard-core commit `5f399234`.
- **Recon path rows now require a leading separator on query and body values.** Whole-value recon rows whose leading path separator is optional (the extension-path row plus the product/config/doc rows such as `default`, `sap`, `actuator`, `cgi-bin`, `README.md`, `credentials.json`) no longer flag ordinary bare-word field values in `query_param` and `request_body` contexts: outside `url_path`/`unknown` contexts the matched value must itself start with `/` or `\` to count as a recon probe. Separator-prefixed probe values (`/default.asp`, `/actuator/health`, `/cgi-bin/test.cgi`) and bare words used as the URL path still detect. Parity with upstream guard-core issue #115 (fix PR #116); the set of affected rows is derived from the pattern table by the same optional-separator anchor rule as the Python engine.
- **Display redaction collapses the whole value when the JSON depth cap trips.** A header or blob whose JSON nesting reaches the display-redaction depth cap (32, matching Python's `detection_max_json_depth` default) now redacts to a single `[REDACTED]` instead of emitting a huge half-redacted structure; nesting under the cap keeps the in-place redaction shape. Parity with upstream guard-core commit `8bae9459`.
- **Console-safe activity log lines.** The log-bound `Reason` and `TriggerInfo` fields (detection-derived text such as matched-pattern previews and body excerpts) are escaped to pure ASCII: literal `\n`/`\r`/`\t` escapes, `\xNN` for raw invalid UTF-8 bytes (the counterpart of Python's surrogate-escaped bytes), and `\uXXXX` for other control or non-ASCII characters, so log lines can never break on legacy console encodings such as Windows cp1252. The block stash, block hook payloads, and threat `match` reporting values are untouched. Parity with upstream guard-core commit `f5d53ca5`.

-------------------

Full parity with guard-core 4.0.4, binary-noise gates, and the /v4 module path (v4.0.4)

### Breaking Changes

- **Import paths now end in `/v4`.** The module path is `github.com/rennf93/guard-core-go/v4` and the release tag is `v4.0.4`; Go modules reject a `v4+` tag unless the module path carries the `/v4` suffix, so the migration is mandatory for this release to be fetchable. Installation is now `go get github.com/rennf93/guard-core-go/v4@v4.0.4`. The earlier `v0.1.0` tag was a burned pre-release snapshot of the port and remains on the un-suffixed path.

### Added

- **Full check parity with the Python guard-core 4.0.4 engine: 17/17 security checks.** The port now covers the complete check catalogue of the Python engine, including the 4.0.x additions.
- **Binary-noise gates for detection, including the SQLi comment-terminator binary gate.** Pattern sources prone to firing inside text-decoded binary bodies (PDFs, compressed streams) are registered in a noise-prone registry and gated by binary-density analysis, while genuine ASCII-region matches still detect. The SQLi comment-terminator source joins the registry in this release (parity with upstream guard-core `f5d53ca5`): the pattern's apostrophe-plus-whitespace-before-`--` shape routinely matched `0x27 0x0A 0x2D 0x2D`-style byte runs inside binary content.
- **Corpus harmonization with guard-core 4.0.3/4.0.4.** The conformance corpus tracks the Python engine's fixtures at spec 4.0.3/4.0.4, including binary-body vectors, so the two engines are validated against the same detection expectations.
- **Interop harness at 82/82.** The cross-implementation runner (`go test -tags interop`) executes the Python-engine fixture corpus against the Go engine with full agreement.

### Changed

- **Makefile harmonized with the Python guard family.** `install`, `test` (unit plus `-tags integration` in docker), `lint` (`gofmt` check plus `go vet`), `bump-version` (via `.github/scripts/bump_version.py`, which scaffolds this changelog) and `clean` match the conventions used across the Python guard repos.
