# AGENTS.md
Guidance for AI agents (including Claude Code) working in this repository.

## Project Overview

guard-core-go is the Go core engine library of the guard-core API security ecosystem. It is a library, not an application: there is no `package main`, no binary, and nothing to `go run`. The module path is `github.com/rennf93/guard-core-go` (go.mod `go` directive: `1.25.0`). The README is intentionally minimal (two lines); this file, the code, and CI are the real documentation.

The single library package lives in `guardcore/` at the repo root. Its exported surface is:

- `Engine` facade: `NewEngine(cfg *SecurityConfig) (*Engine, error)` wires `SecurityConfig`, `RouteRegistry`, `RedisManager`, `IPBanManager`, `RateLimitManager`, and the package-level `DefaultCloudManager` into a composed engine, then `BuildDefaultPipeline` assembles the ordered checks pipeline. Methods: `Initialize()` (sync.Once guarded startup: Redis connect, cloud ranges, ban/rate-limit initialization), `Check(req Request) *Response`, `CreateErrorResponse`, `Close`.
- Checks pipeline: the `SecurityCheck` interface (`CheckName`, `AppliesTo`, `EnforcedOnExcludedPaths`, `Check`) and `SecurityCheckPipeline` executing 17 named checks in a fixed slot order defined in `buildChecks` (`guardcore/pipeline.go`) and mirrored in `CheckNameValues` (`guardcore/config.go`): `route_config`, `emergency_mode`, `https_enforcement`, `request_logging`, `request_size_content`, `required_headers`, `authentication`, `referrer`, `custom_validators`, `time_window`, `cloud_ip_refresh`, `ip_security`, `cloud_provider`, `user_agent`, `rate_limit`, `suspicious_activity`, `custom_request`.
- Detection: `Detect(content, ip, context) DetectResult` runs the regex pattern table (`guardcore/pattern_table.go`) over preprocessed views of the content (URL-decoded, base64-decoded, gzip-inflated, unicode-normalized), plus semantic analysis, across 19 categories listed in `AllDetectionCategories` (xss, sqli, cmd_injection, path_traversal, and others).
- Managers: `IPBanManager` (ban/unban/is-banned with network bans), `RateLimitManager` (Lua-scripted sliding windows via Redis, per-endpoint buckets, autoban), `CloudManager` (cloud provider IP range blocking for AWS/GCP/Azure/DigitalOcean/Linode/Vultr with region carve-outs), `RedisManager` (key-value facade over go-redis), `RouteRegistry`/`RouteConfig` (per-route overrides that bump a revision counter to trigger pipeline rebuilds).
- Request model: the framework-agnostic `Request` interface plus `RequestOptions`, `RequestFactory`, `Response`, `ResponseFactory`, `Headers`, `RequestState` (per-request bypass flags, block stash, route resolution).
- Logging: `ActivityLogger` interface and redaction helpers (`RedactSensitiveHeaders`, `RedactBlobForDisplay`, `RedactURLForDisplay`) that mask sensitive headers, params, and body fields.

The shipped release is the tag `v0.1.0` (pointing at commit `73f8dd3`). This is an early, actively developed port; do not assume API stability.

## Ecosystem Position

guard-core-go is the Go port of the guard-core security engine. The reference implementation is the Python guard-core engine: the conformance fixture corpus (`conformance/guard-core-spec-4.0.3/`) states in `CORPUS.md` that expected values were generated by running the reference engine (guard-core, enhanced/4.x detection path) and must never be hand-written. The two implementations are kept behaviorally compatible by:

1. The conformance suite (`conformance/conformance_test.go`), which replays the shared JSON fixture corpus against `guardcore.Detect` and compares verdicts field by field.
2. A cross-implementation Redis interop harness (`guardcore/interop_runner_test.go`, build tag `interop`) where the Go and Python engines share one Redis instance (prefix `guard_core_interop:`) and verify each other's persisted state: bans, rate-limit buckets, legacy-key migration (spec 09), and the `cloud_ip_v2` payload format.

Framework integration happens in separate adapter repositories, not here. The adapter for Go `net/http` is `nethttp-guard`: it translates `net/http` request types into `guardcore.Request` and translates `guardcore.Response` back into framework responses. The `adapters/` directory at the repo root is currently an empty placeholder and is not tracked by git (git does not track empty directories), so do not expect it to appear in fresh clones.

## Boundary Rules

The architecture is a strict core/adapter split. These rules are backed by the actual imports and code:

- MUST NOT add framework-specific code to `guardcore/`. There is no HTTP server, routing, middleware, or web framework code in the package. Verified imports across `guardcore/*.go` (non-test): Go stdlib plus exactly three third-party modules (`github.com/dlclark/regexp2`, `github.com/redis/go-redis/v9`, `golang.org/x/text/unicode/norm`). The only `net/http` use in the core is the outbound HTTP client in `guardcore/cloudproviders.go` that fetches provider IP range data.
- MUST NOT put security logic in adapters. Framework adapters such as `nethttp-guard` (Go `net/http`) only wire framework types to the core `Request`/`Response` interfaces. All detection, banning, rate limiting, cloud blocking, and response decisions live in `guardcore/`. If you find yourself writing an `if` about threats or bans in an adapter, it belongs in the core.
- MUST NOT change `Detect()` verdicts, scores, or the `DetectResult` shape without regenerating the conformance fixtures from the reference engine. Expected values are generated, never hand-written (`conformance/guard-core-spec-4.0.3/CORPUS.md`).
- MUST keep new checks inside the established contract: implement `SecurityCheck`, add the check name to `CheckNameValues` in `guardcore/config.go` (config validation rejects unknown names, e.g. for `muted_check_logs`), and register it in the fixed slot order in `buildChecks` (`guardcore/pipeline.go`). Slot order is part of the spec.
- MUST keep unsupported features failing closed. `SecurityConfig.Validate()` returns `UnsupportedFeatureError` for features this port does not implement yet (global behavior rules, dynamic rules, agent telemetry, CORS, geo blocking). Do not silently no-op them.
- MUST NOT push to `master` (protected), and MUST NOT create tags or releases. The release gate workflow runs only on `v*` tags pushed by maintainers.
- MUST NOT commit `.DS_Store` or `KNOWN_GAPS.md`. Both are local-only; `KNOWN_GAPS.md` is the maintainer's internal working notes and is explicitly gitignored.
- MUST NOT add third-party dependencies casually. `go.mod` has exactly three direct dependencies; new ones need a strong justification because this is a security core.

## Quick Start

Prerequisites: Go 1.25 or newer (go.mod requires `1.25.0`; CI tests `1.25.x` and `1.26.x` with `GOTOOLCHAIN=auto`). For integration tests, a reachable Redis 7 instance. There is no Makefile; commands are plain `go` commands plus the exact steps CI runs.

```
git clone https://github.com/Guard-Core/guard-core-go
cd guard-core-go
go build ./...
go test ./...
REDIS_HOST=127.0.0.1 go test -tags integration ./...   # needs local Redis on 6379
```

There is nothing to `go run`: the module builds a library consumed by adapter repos.

- `guard-core-spec-4.0.3/CORPUS.md`: authorship and drift rules for the corpus; expected values come from the reference engine.
- `guard-core-spec-4.0.3/cases/`: suites `benign`, `boundaries`, `cmd_injection`, `context_matrix`, `encoding`, `inclusion_sensitive_recon`, `index`, `misc_injection`, `path_traversal`, `semantic`, `sqli`, `xss`.

## Testing & Conformance

Four layers, all runnable with the commands above:

1. Unit tests (no build tag): extensive in-package tests in `guardcore/*_test.go` (pipeline slot order, route guards, config validation matrix, redaction vectors, ban lifecycle with fake Redis handlers, cloud selector grammar including `:!region` carve-outs, single-flight refresh, fail-open/fail-closed behavior).
2. Integration tests (build tag `integration`): six files (`cloud_integration_test.go`, `composition_integration_test.go`, `ipban_integration_test.go`, `pipeline_integration_test.go`, `ratelimit_integration_test.go`, `route_integration_test.go`) with ~25 `TestIntegration*` functions. Every test reads `REDIS_HOST` from the environment and skips when it is unset, so a bare `go test ./...` stays green without Redis. CI provides Redis via a `redis:7-alpine` service and sets `REDIS_HOST=127.0.0.1`.
3. Conformance suite (no build tag, part of `go test ./...`): `conformance/conformance_test.go` replays the shared JSON corpus against `guardcore.Detect`. If you change detection behavior and the corpus disagrees, the fix is either reverting your change or regenerating fixtures from the reference engine, never editing expected values by hand.
4. Interop harness (build tag `interop`): `guardcore/interop_runner_test.go` `TestInteropRunner`. Environment: `INTEROP_PHASE` (required), `REDIS_HOST` (required; the test fails rather than skips without it), optional `INTEROP_INPUT` and `INTEROP_REPORT_FILE` (writes a JSON report for the interop orchestrator). It operates on shared Redis at `REDIS_HOST:6379` under prefix `guard_core_interop:` and checks: bans written by the Python phase (including `::ffff:` mapped spellings), the spec 09 legacy-key migration (byte-exact values, preserved PTTL, legacy keys deleted), rate-limit zset bucket outcomes, the `banned_networks` wire grammar, and byte-exact `cloud_ip_v2:AWS` payload round-trips with the `us-east-1` carve-out.

Fail-secure behavior is itself tested: validator panics fail closed, Redis unavailability during startup fails open only when `RedisFailOpen` is set, and unpopulated cloud caches fail open until the first refresh.

## Code Quality Standards

- `gofmt` clean: CI's gofmt step fails the build on any output from `gofmt -l .`.
- `go vet ./...` clean on every push and weekly.
- `govulncheck ./...` clean; dependency bumps land as commits like `build(deps): bump golang.org/x/text to v0.39.0 (GO-2026-5970)`.
- Conventional commits, matching existing history: `feat(guardcore): ...`, `test(guardcore): ...`, `fix(checks): ...`, `ci: ...`, `docs: ...`, `chore: ...`, `build(deps): ...`. Subjects are detailed and spec-referencing; follow that style.
- Security invariants worth preserving (all asserted by tests): every detection regex carries a match timeout; validators that panic fail the request closed rather than open; blocked responses go through `createErrorResponse` honoring `CustomErrorResponses`; `on_block` hooks are suppressed for `custom_request`, `custom_validators`, and `https_enforcement`; passive mode suppresses blocking responses everywhere.
- No attribution footers, no generated-file noise in commits.

## Development Workflow

1. Branch from `master` (the default and protected branch; never push directly to it, never merge into it yourself).
2. Make the change in `guardcore/` (or `conformance/` fixtures following `CORPUS.md` rules).
3. Run locally: `gofmt -l .`, `go vet ./...`, `go test ./...`, and if Redis is available locally: `REDIS_HOST=127.0.0.1 go test -tags integration ./...`.
4. Commit with the conventional style shown in `git log` (detailed subjects, scope `guardcore` for package changes).
5. Push your branch and open a PR; CI (tests + govulncheck + CodeQL) runs on the PR.
6. Keep `KNOWN_GAPS.md` and `.DS_Store` untracked; the maintainer maintains `KNOWN_GAPS.md` locally as internal working notes.
7. Releases are tag-driven and maintainer-only: pushing a `v*` tag triggers the release gate workflow; do not create tags or releases as an agent.

## Best Practices

- Build configs with `NewSecurityConfig(mutate)` so `Validate()` always runs; `DefaultSecurityConfig()` returns a secure-by-default config (`FailSecure: true`, Redis enabled, all detection categories on, `guard_core:` prefix).
- Call `Engine.Initialize()` before the first `Check()`; it is idempotent via `sync.Once` and wires Redis-backed state and cloud ranges. `Engine.Close()` closes Redis.
- Treat `SecurityConfig` and `RouteRegistry` as long-lived and mutable under revision control: `SecurityConfig.BumpRevision()` and `RouteRegistry.Register` (which bumps the registry revision) drive automatic pipeline rebuilds on the next request; do not defeat this caching with ad hoc reconfiguration.
- `DefaultCloudManager` is a package-level singleton shared by all engines in a process; cloud provider state (stores, refresh stamps) is process-global by design.
- Keep `RequestOptions` the only way to construct requests in tests and adapters (`NewRequestFactory().CreateRequest(opts)`); do not reach into `guardRequest` internals.
- Preserve the regex timeout budget: patterns compile through `compileRE` with `Config.CompilerTimeout`; new patterns in `pattern_table.go` must tolerate the timeout and the `\Z` translation handled by `translatePattern`.
- Use the redaction helpers for any logging of request data; never log raw `Authorization`, `Cookie`, or API key headers, and honor `MutedCheckLogs`.
- When adding a check, mirror all four `SecurityCheck` methods faithfully: `EnforcedOnExcludedPaths` decides whether exclusion-scoped requests still run the check; `AppliesTo` keeps disabled checks out of the built pipeline entirely.
- IP comparison must go through the canonicalization helpers (`CanonicalizeIP`, `ipMatchesList`) so that `::ffff:` mapped addresses and CIDR entries match consistently; this is pinned by interop tests.

## Related Projects

- guard-core (Python): the reference implementation of the engine. It generates the conformance corpus expected values and is the other participant in the Redis interop harness described in `guardcore/interop_runner_test.go`.
- nethttp-guard: the Go `net/http` framework adapter. It wires `net/http` request types into `guardcore.Request` and `guardcore.Response` back into HTTP responses, and contains no security logic itself.
